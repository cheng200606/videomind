## 三、关键决策

1. **音源用离线 TTS 合成**（Windows SAPI 中文语音），不用真实人声素材：红线禁止素材入库，TTS 音源纯本地生成、内容自写，且对「转写→结构化→导出」机械链路的验证是等价的；报告中明确标注合成音源与「识别结果仅供参考」口径。若本机无中文语音包则退回英文讲座（链路验证等价，产物语言如实记录）。
2. **E2E 用 audio-only MP4**：本轮 OCR 引擎为 none（沿用用户现有引擎设置，画面通道已在 v0.12 打包烟雾中验证过），音频轨即可走完转写→结构化→导出全链路，生成更快。
3. **跑在用户 dev 数据目录**（SQLite 覆盖 + `.env` 的 Key）：Key 只在 `.env`，必须读它；新增一个明确命名的批次，报告中注明可删。
4. **`.env.example` 的 MySQL/Redis 行改为注释默认**：与「可选覆盖」注释对齐，消除「照抄示例即启动失败」的坑（本轮实测踩中）。

### E2E 时间线与数据

- 转写（whisper tiny int8 + VAD，CPU）：36.7 分钟音频 → **101 秒**；562 段 / 转写正文 10418 字 → 渲染后 ~18300 字符 → **切 2 块**
- 结构化（首轮，max_tokens=4000）：两块全部失败——输出在 token 上限处截断（`Unterminated string (char 8022)`），原样重试必然再失败 → 视频 FAILED
- 修复后重跑（max_tokens=8000 + 抢救 + 精简重试）：块 1 ~21s、块 2 ~15s，**批次 succeeded**
- 产物：33 条（1 内容总结 + 31 知识要点 + 1 UML 草稿），置信度 26 明述 / 5 推断 / 2 低置信——LLM 真实产出（规则兜底只会有 ≤12 条全明述）；要点标题是提炼（如「阻塞的根源」「三种历史解决思路」）；低置信条目附「语音含糊」原因
- 导出：批次头 + 覆盖提示块 + 一句话结论 + 章节大纲 + Mermaid 流程图 + 带证据链的要点（quote 保留原始转写，含 tiny 模型在合成音源上的繁简/同音瑕疵——如实呈现，正文由 LLM 规范化）

### 实测发现并修复的三个问题

1. **max_tokens=4000 截断**（致命）：稠密转写的结构化输出超上限，JSON 断裂，原样重试无效。修复：结构化调用上限提至 **8000**；system 提示词加输出规模约束（≤15 条、content ≤120 字）；解析失败且具备截断特征时**抢救已完整的条目**（`_salvage_truncated`，`report.output_salvaged` 如实上报 + 用户可见提示）；重试消息改为「精简条目重新输出」。新增 2 例单测。
2. **分块锚点相对化**（数据质量）：第二块章节锚点被模型输出成本段相对时间（2:14/2:37…），跳转会错位。两轮提示词加固仍不稳定（第三轮甚至把分钟数当毫秒）——**最终采用确定性设计：分块输入时间归零（相对本段），模型只输出相对毫秒，`_rebase_draft` 在合并时按块起点回移并夹取范围**。第四轮实测：17 章节全部绝对时间、严格有序、无缝覆盖全片；31 要点锚点全部落在片长内。新增 1 例单测。
3. **`.env.example` 自相矛盾**：注释说 MySQL/Redis 是「可选覆盖」，两行却处于激活状态——照抄示例填 Key 的用户（本轮实测踩中）在没有 MySQL 的机器上应用直接起不来。修复：默认注释 + 说明只有真起了服务才取消注释。
