# 桌面版发布方案 — 发布形态 / 差分死因 / 增量更新 / 资源分离

日期：2026-11-07 · 作者：程夏（组长）· 数据基线：v0.12.0 实测（Release 已发布）+ 0.12.1 对照实验

## 一、结论先行（全部有实测数字背书）

| 命题 | 实测结论 |
|---|---|
| 「用 ZIP 替代 exe 减小体积」 | **不成立**：同内容 ZIP 338MB > NSIS 271MB（DEFLATE 压不过 solid LZMA）。ZIP 价值=免安装（机房/无权限演示机），保留双附件 |
| 「模型资源分离，本体几十 MB」 | **前提不成立**：包内可分离权重只有 RapidOCR 的 3 个 ONNX 共 **31MB**（占 11%）；Whisper ~75MB 权重本来就按需下载。其余 99% 是运行时 DLL + Electron 壳，不是权重 |
| 「electron-updater 差分更新省流量」 | **对我们结构性失效**：NSIS 安装包内嵌构建时间戳，同版本两次独立构建即 **99% 块不同**（§四）——每次发版用户全量重下 259MB，这才是「更新太重」的根因 |
| 「增量更新包（自研）」 | **有效且已验证生成端**：0.12.0→0.12.1 的 update.zip = **103.5MB**（§五），且瓶颈明确可解释 |
| 「程序本体几十 MB」 | **Electron 架构下不存在**：VideoMind.exe（纯 Electron 壳）解包 238MB / 压缩 ~101MB，是物理下限；几十 MB 只能换非 Electron 壳（范围外） |

**推荐路线**：阶段 1 双附件（已落地）→ 阶段 2 自研增量更新包（应用端 1–2 天，更新下载 259MB→~103MB）→ C 级引擎运行时分离（周会评审）。OCR 权重独立拆分否决（§六）。

## 二、体积构成实测（决策依据）

解包 765MB（`win-unpacked`）→ NSIS 271MB / ZIP 338MB：

| 组件 | 解包体积 | 说明 | 可分离性 |
|---|---|---|---|
| VideoMind.exe（纯 Electron 45 壳，无业务） | **238MB** | 每版会被重写（asar 完整性 + 版本资源 patch），压缩后 ~101MB | 不可拆，换壳才可减 |
| Python 3.14 + FastAPI/SQLModel 业务栈 + 业务代码 | ~60MB | sidecar 骨架 | 无意义（产品本体） |
| Whisper 运行时（ctranslate2 62 + av 63 + numpy 21 + tokenizers 等） | ~190MB | 纯 DLL/代码，**不是权重** | C 级可拆 |
| OCR 运行时（onnxruntime 43 + cv2 113 + shapely/pyclipper 等） | ~170MB | 纯 DLL/代码 | C 级可拆 |
| OCR 模型权重（PP-OCRv6 det/rec/cls 三个 ONNX） | **31MB** | 唯一在包内的权重 | 独立拆分否决（§六） |
| Whisper 模型权重 | **0**（按需下载） | 首次转写自动下载 tiny ~75MB | **已分离 ✓** |

## 三、阶段 1（已落地配置）：双附件发布

| 附件 | 用途 | 体积（v0.12.0 实测） |
|---|---|---|
| `VideoMind-Setup-x.y.z.exe` + `.blockmap` + `latest.yml` | NSIS 安装版；electron-updater 全量通道 | 271MB |
| `VideoMind-x.y.z-win.zip` | **便携版**：解压双击 `VideoMind.exe`，适合无安装权限的机器 | 338MB |

已落地改动：

- `desktop/electron-builder.yml`：`win.target = [nsis, zip]`，一次 `npm run dist` 出双产物（zip 目标**不生成 blockmap**，无自动更新，升级=覆盖解压）
- `desktop/package.json`：`dist` 脚本从写死的 `--win nsis` 改为 `--win`（**CLI target 覆盖 yml 配置**——实测踩坑），另留 `dist:nsis`
- `desktop/publish_release.py`：发布单命令工具（建 Release + 流式传资产 + 核验 state=uploaded；同尺寸跳过、不一致删传；PAT 走 git credential fill 不回显不落盘）
- 便携版说明：数据默认仍写 `%APPDATA%\VideoMind\data`，可设 `VMIND_APP_DATA_DIR` 隔离实现 U 盘便携；**便携版与安装版不要同时运行**（共享数据目录，实测第二实例自行退出）

## 四、差分更新为何失效（对照实验）

electron-updater + blockmap 的差分机制本应「只下变更块」，实测两组对照：

| 对比 | 结果 |
|---|---|
| released v0.12.0 → 本地重构建 0.12.1（版本号变更） | 变更块 **12936/12939，差分下载 ~259MB（99%）** |
| released v0.12.0 → 本地重构建 **同版本** 0.12.0 | 变更块 **12934/12936，~259MB（99%）** |

同版本两次构建就 99% 不同 → builder 把构建时间戳等元数据写进了压缩流头部，其后的全部块级联失效（app-builder-lib 的 NSIS 头 zlib 压缩 + 7z payload 元数据）。**结论：electron-updater 差分通道对任何「两次独立构建」都退化为全量下载，不可依赖**；调 compression 参数救不了（级联在文件布局层）。实测脚本方法存档于方案评审记录，无需再测。

## 五、阶段 2（主推）：自研文件级增量更新包

### 生成端（已交付：`desktop/make_update_zip.py`）

对比上一版与当前版的 `win-unpacked`，逐文件 sha256 比对，只打包有增改的文件，同时产出 manifest（files[path,sha256,size,action] / deleted[] / zip_sha256）。

**0.12.0 → 0.12.1 实测**（仅版本号变更，前端 asar 变、sidecar 未变）：

| 文件 | 解包 | 说明 |
|---|---|---|
| VideoMind.exe | 238.3MB | 每版被重写：asar 完整性 hash + 版本资源 patch（builder 源码 `ElectronFramework.js:51` 证实） |
| resources/app.asar | 2.1MB | 前端业务 |
| resources/elevate.exe | 0.1MB | 首次出现 |
| **update.zip 合计** | **103.5MB 压缩** | vs 全量便携 338MB = 3.3× |

典型发版（前端+后端业务都变）：+ `resources/backend/VideoMindBackend.exe`（~2-3MB 压缩，业务代码在 PYZ 内）→ update.zip **~103–107MB**。Electron 壳那 ~101MB 是每版必付的版本资源 patch 成本，压不掉。

### 应用端（待实施，1–2 天，周会通报后动工）

1. main.js 启动/定时拉 `update-manifest-x.y.z.json`（GitHub Release 附件，HTTPS）
2. base_version 匹配才允许增量（不匹配→回退全量 NSIS 通道）；下载 update.zip → 逐文件 sha256 校验（manifest 自带 zip_sha256 双重校验）
3. 写入 `pending/` 目录 → 提示用户退出 → 退出后由小替换脚本落位（Windows 文件锁：运行中不可覆盖自身，脚本内含失败回滚：旧文件先备份为 `.bak`）
4. 完整性口径：electron 的 asar 内建校验覆盖不到自更新替换，**防篡改由 manifest sha256（HTTPS + GitHub）承担**——课程项目可接受，写进方案
5. electron-updater（NSIS 全量通道）保留，作为增量不可用时的兜底

## 六、明确不做：OCR 模型权重独立 ZIP

- 收益：31MB 解包；ONNX 是已压缩二进制（protobuf+float），ZIP 再压几乎不缩 → 实省 ~30MB = 11%
- 代价四件套：打包态 rapidocr 模型目录参数化（改 `ocr.py` `_load`）、启动检测与「缺少模型」下载引导 UI、解压落位与版本匹配、失败恢复（半截文件/磁盘满/版本不匹配）
- Whisper 权重按需下载（HF 镜像内置）就是既有的「模型单独下载」机制
- 结论：**否决**；若 C 级立项，OCR 权重随 OCR 引擎包一起走

## 七、C 级设计：引擎运行时分离（周会评审件，未实施）

- **主包**：Electron 壳 + Python/FastAPI 骨架 + 业务 → 估 **110–130MB**
- **引擎包**（独立版本号，随 `requirements-engines.txt` 锁版本）：
  - `videomind-engine-whisper-x.y.z.zip`：~190MB 解包 → 估 90–110MB
  - `videomind-engine-ocr-x.y.z.zip`：~170MB 解包（含 31MB 权重）→ 估 80–95MB
- **机制**：sidecar 启动扫 `%APPDATA%\VideoMind\engines\{name}\{version}\` 注入 `sys.path`；引擎可用性沿用 `is_available()` 注册表——包缺失时 `available_ocr()` 自然降级，设置页显示「引擎包未安装 → 下载链接」，零新契约；manifest（sha512 + 兼容主包版本区间）校验后解压；保留完整离线安装包兜底
- **收益重估**（结合 §五）：主包 110–130MB；更新时 VideoMind.exe 版本资源 patch ~101MB 仍是每版必付 → 增量更新体积与阶段 2 相当，C 级的主要收益在**首装体积**与**引擎包跨版本复用**
- **成本/风险**：3–4 天 + 每版多打两个包；PyInstaller 多目录 import 顺序、引擎包与 Python 3.14 强绑定、下载失败率、演示多一步安装
- **结论**：评分若不要求「小首装」，阶段 2 已覆盖真实痛点；C 级建议 W6 周会评审后决定

## 八、后续发布操作手册（固化）

```bash
# 1. 版本号：desktop/package.json → x.y.z（CHANGELOG 先补条目并署名）
# 2. 后端：backend/ 下重建 sidecar + 烟雾验证（命令见 AGENTS.md「桌面版」条目）
.venv/Scripts/pyinstaller VideoMindBackend.spec --noconfirm
# 3. 桌面：双产物（NSIS + ZIP）
cd desktop && npm run dist
# 4. 增量包（阶段 2 应用端落地后接入发布；生成端已可用）：
#    保留上一版 win-unpacked 副本，然后
backend/.venv/Scripts/python desktop/make_update_zip.py \
    --from release/win-unpacked-prev --to release/win-unpacked \
    --version x.y.z --base a.b.c --out release/VideoMind-update-x.y.z.zip
# 5. tag 与推送
git tag vx.y.z && git push origin develop vx.y.z
# 6. 发布（PAT 走 git credential fill，不回显）
backend/.venv/Scripts/python desktop/publish_release.py --tag vx.y.z \
  --notes desktop/release/notes-vx.y.z.md \
  --assets desktop/release/VideoMind-Setup-x.y.z.exe \
           desktop/release/VideoMind-Setup-x.y.z.exe.blockmap \
           desktop/release/latest.yml \
           desktop/release/VideoMind-x.y.z-win.zip
# 7. 核验：匿名拉线上 latest.yml 对 version+sha512；CHANGELOG 补发布行
```

注意事项（沿用 AGENTS.md 已知坑）：PyInstaller 与 vite 构建必须串行（本机 commit limit 29/32GB）；后台构建别用管道接 tail；改完 run_server.py 等源码必须重建 sidecar；构建期间 shell 工作目录别停在 `release/win-unpacked` 里（Windows 目录占用会导致 EBUSY）。
