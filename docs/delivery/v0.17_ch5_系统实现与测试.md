### 5.2.3 三个选型取舍（附理由与代价）

1. **不用 `openai` SDK，改用 `httpx` 直连 OpenAI 兼容协议**（`backend/app/llm.py`）。原因是 `openai` 依赖的 `jiter` 0.18.0 没有本机 Python 3.14 / win_amd64 轮子，装不上。代价是要自己处理 JSON mode 不支持时的降级重试，这段逻辑集中在 `llm._post_chat`，改模型接入时只动这一处。
2. **前端不引播放器库**，用原生 `<video>` + 自绘 `EvidenceTimeline.vue` 刻度条。代价是播放器能力有限（无逐帧拖拽），收益是零依赖、时间锚点完全可控，且避开了第三方播放器在 Electron 中的授权与打包问题。
3. **重引擎分列 `requirements-engines.txt`**，不进主依赖。`faster-whisper==1.2.1` + `av==18.1.0` 锁版本，因为 `av` 19 移除 `metadata_errors` 会直接弄坏 `yueying` 的适配层。代价是新机器想跑真实 ASR 需要额外一步安装。

## 5.3 关键功能实现

### 5.3.1 四阶段主链路

解析主链路实现在 `backend/app/pipeline.py:291` 的 `parse_video()`，按「转写 → 画面 → 结构化 → 产物」顺序执行，任一阶段失败只影响本条视频，批次进 `PARTIAL`。

| 阶段 | 枚举值 | 实现位置 | 状态落点 |
| --- | --- | --- | --- |
| ① 音频通道（ASR 转写） | `transcribe` | `pipeline.py:306-342` | `video.transcribe_status` |
| ② 画面通道（关键帧 + OCR） | `visual` | `pipeline.py:344-354` | `video.visual_status` |
| ③ LLM 结构化 | `structure` | `pipeline.py:356-369` → `llm.py:291` | `video.structure_status` |
| ④ 产物生成与落库 | `artifact` | `pipeline.py:_persist`（`pipeline.py:433`） | `video.artifact_status` |

阶段枚举定义在 `backend/app/enums.py:4`（`Stage`），状态枚举在同一文件 `enums.py:16`（`StageStatus`，含 `skipped`）。**`skipped` 是真实分支不是占位**：`pipeline.py:345` 在 OCR 未启用或无关键帧时把画面通道置为 `SKIPPED`，对应产品定义里「无字幕降级 / OCR 关闭」的异常态。

### 5.3.2 三个可插拔策略的实现

产品定义 §五 列出的三个策略在代码中落在两处：引擎侧用 Protocol + 注册表，产物侧用 Protocol + 策略类。

表 5-4 可插拔策略落点

| 策略 | 协议定义 | 实现类 | 选择方式 |
| --- | --- | --- | --- |

三个策略的共同设计点：**新增一种引擎或一种产物只加实现类并挂进注册表，不改主链路**。引擎注册表在 `backend/app/engines/__init__.py`（import 即注册），产物注册表是 `artifacts.py:232` 的 `REGISTRY` 字典。

> **已知实现缺口（如实记录）**：`artifacts.resolve()`（`artifacts.py:240-241`）用 `[REGISTRY[n] for n in names if n in REGISTRY]` 过滤，**未知名会被静默丢弃**。请求侧有校验，但启动读回 `settings.json` 的路径没有，理论上存在「产物集合被清空而阶段仍报成功」的风险。该问题已登记为 v0.17 待修项，本章按当前实现如实描述。

### 5.3.3 单批次互斥：`ParseMutex`

同一时间只允许一个批次解析，这条约束由 `backend/app/pipeline.py:137` 的 `ParseMutex` 在进程级强制：

- `claim(batch_id)`（`pipeline.py:150`）——集合非空即拒绝，返回 `False` 由路由转成 409；
- `release(batch_id)`（`pipeline.py:157`）——后台任务 `finally` 中释放；
- 三个入口（新建解析、重新解析、单条重试）都要先 claim，占用时返回 409。

设计理由是 SQLite 并发写会撞锁，且先完成的批次状态重算会把仍在解析的批次提前置终态（见 `ParseMutex` 类文档字符串）。进程重启后集合自然为空，孤儿 `RUNNING` 行由 `pipeline.recover_orphan_runs`（`pipeline.py:569`）恢复。

### 5.3.4 长转写的分块结构化

`llm.structure()`（`backend/app/llm.py:291`）对长转写按段边界切块、逐块调用模型后合并，避免整条视频被整体截断。两个实现要点：

1. **锚点用确定性设计而非提示词约束**：每块输入的时间归零（相对本段开始），模型只输出相对毫秒，合并时 `_rebase_draft()`（`llm.py:272`）按块起点回移并夹取。
2. **不允许静默丢内容**：分块数、失败块、截断事实与抢救情况都通过 `report` 字典回传给 `pipeline`，再转成事件流提示与摘要产物的 `notice` 字段。

无 API Key 时走 `llm.fallback_draft()`（`llm.py:361`）的规则兜底：按段数等分切章、取长句为条目，并置 `report["fallback"] = True` 供上层写入提示。**这条路径的产物是规则草稿，不能当作模型效果展示**，本章与答辩口径都按此说明。

**一处如实记录的局限**：合并阶段 `conflicts` 是按块收集后再拼接（`llm.py:352`），因此**跨块的前后矛盾无法检出**——模型只在本块时间范围内比对，两块之间的表述冲突不会进入 `ConflictRecord`。要跨块检出，需要在合并收尾调用（`llm.py:252`）里再喂一遍全部条目的摘要，成本与截断风险都会上升，故未采用；本章把它列为已知边界而非缺陷。

### 5.3.5 代码块产物的真实状态（重要）

代码块产物由**画面通道（OCR）**触发，不是由文本通道触发。证据在 `artifacts.py:193-201`：`CodeBlocksStrategy.build()` 的第一句就是 `if not ctx.ocr: return []`，只有 OCR 识别出的帧文字才会被拼成代码块；生成的条目 `channel` 固定标 `Channel.OCR`（`artifacts.py:225`），以便证据抽屉区分「看到的」与「听到的」。

由此推出三条必须如实写进文档的结论：

1. **`OCR_ENGINE=none` 时不可能产出代码块**。当前开发库的实测分布是 `KEY_POINTS 67 / SUMMARY 4 / UML_DRAFT 4`、`CODE_BLOCKS` 为 0 条，且 4 条视频的 `visual_status` 全为 `SKIPPED`——这正是 OCR 未启用的直接结果，不是代码缺陷。
2. **产出代码块的前置条件是 `OCR_ENGINE=rapid`**（或 `paddle` / `vision`）且视频画面里有可识别的代码文字。v0.17 取证已用合成素材（见下方演示素材声明）在隔离库中跑通：`OCR_ENGINE=rapid` + mock ASR，items 共 23 条（`key_points` 15 / `code_blocks` 6 / `summary` 1 / `uml_draft` 1），6 条代码块 `channel` 全为 `ocr`，`anchor_ms` 分别为 0 / 30000 / 60000 / 90000 / 120000 / 150000，每块 8 行、147–261 字符，四阶段 `transcribe / visual / structure / artifact` 全部 `done`（`visual` 阶段在 v0.17 之前一直为 `SKIPPED`，这是第一次真正执行完成）。**该结果只能证明链路可跑通，不能用于评价识别质量**——素材是合成的，且 OCR 仍然丢失缩进。
3. **画面去重对连续滚动的代码偏保守，可能只保留少量帧**。`ocr.py:25` 的 `dedupe_frames()` 与 `frames.py:29` 的 `sample_frames()` 共用同一口径 `SIMILAR_THRESHOLD = 6.0`（`frames.py:17`，16×16 灰度缩略图均值差）：完全相同的课件页会被丢弃，这正是去重的目的；但代码逐行滚动时相邻帧的差值也很小，实测可低到 0.8–0.9，远低于阈值，于是**同一段代码只留下少数几帧**。这是取「省 token」与「不漏画面」之间偏向前者的取舍结果，本章如实记录而不调低阈值——阈值调低会让满屏课件产生大量重复帧，token 与 OCR 耗时同步上升。若需要完整还原滚动代码，正确做法是改按行滚动量而非整帧均值差判定，属后续迭代项。

### 5.3.6 证据链与不确定性分级

每条知识条目通过 `knowledge_item.evidence_id` 回指一条 `evidence`（`models.py:63`），证据携带时间戳、原话、片段帧路径与通道（`asr` / `ocr` / `both`）。不确定性用 `Confidence` 三档表达（`enums.py:49`）：`explicit` 明述、`inferred` 推断、`low` 低置信。

代码块策略的置信度递增是示例：第 1 个代码块标 `LOW`，其余标 `INFERRED`（`artifacts.py:221`）——因为首个代码块往往是从画面刚进入代码区时截取的，识别质量最不稳定。

### 5.3.7 实现层面的三条诚实边界

以下三条是 v0.17 取证时确认的实现事实，都直接关系到「产出可信」这一核心卖点，故写在实现小节而不是测试小节。v0.17 不改代码，只如实记录。

- **代码块判定不区分代码与正文**：`CodeBlocksStrategy`（`artifacts.py:193`）只判「画面通道连续 8 行文本」——`artifacts.py:210-212` 的 `if len(buf) >= 8` 满足就切块，**不判断这段文字是不是代码**。满屏文字的小结页同样满足条件，会被当成代码块产出。v0.17 的合成素材实测中，6 个代码块里第 5 块（`anchor_ms = 120000`）渲染出来是「# 05 本节小结：并发不是多线程」的小结页正文，就是这条边界的直接证据。要降低误判需要引入语言特征或版面判定，属后续迭代项。
- **可达性（axe）基线只覆盖页面默认态**：v0.16 的「亮 / 暗 × 8 页 0 violation」是在各页**默认态**（无批次数据、未选文件）下取得的。导出页只有批次进终态才渲染 `MdPreview`，上传页只有选中文件后才生成 `el-upload-list`，这两个状态当时**没有被扫描**。v0.17 复扫在导出页终态与上传页已选文件态下各发现若干违规，已按 P1 处理。本章口径一律写「8 页**默认态**」，不写成「8 页 0 violation」。
- **axe 扫描存在假绿的方法学缺陷（比结果更重要）**：headless 下同一标签页连续导航约 3 次后会被判成 `document.hidden === true`，axe 遇到不可见文档会提前退出，`passes` 桶变空——看起来全绿，实际根本没评估。同页 6 连扫得到 `[29, 29, 29, 0, 0, 0]`，改为**每页新开 target** 后 6 连扫恒定 29。故可达性扫描必须每页新开 target；v0.17 起由 `tools/` 下的扫描脚本按此执行，并把未覆盖的页面状态显式列入报告，不沉默略过。

### 5.4.6 口径说明

1. **11 表口径**：`tag` 与 `tag_binding` 分列为两张表，全校口径按 11 表。
2. **`Video.path` 与 API 边界**：数据库保留本地路径用于解析，但 `/api/batches/{id}` 与 `/api/videos/{id}` 不下发绝对路径，只给 `file_name` + `media_url`。
3. **无用户表**：`note.user_id` 与 `revision.editor` 固定为 `local`；用户注册与权限在范围外，不因数据字典而新增 `user` 表。
4. **`Artifact.payload` 结构**：JSON 字段随 `schema_type` 变化，具体字段由 `backend/app/artifacts.py` 的 Pydantic payload 模型定义，不把某一类的字段写成所有产物的通用字段。
5. **数据字典与模型同源**：本节的字段、类型、约束均取自 `backend/app/models.py`，逐字段核对；改模型必须同步改本节。
