| 维度 | 结论 | 边界（本章如实写明的部分） |
| --- | --- | --- |
| 技术 | 可行 | 四个阶段的实现与测试已落地（`pytest` / `vitest` 全绿）；代码块产物依赖 OCR 画面通道，未启用该通道时产出为 0 条，属配置结果 |
| 经济 | 可行 | 转写与 OCR 在本机运行，无按次计费；成本集中在 DeepSeek 结构化调用，按 token 计费且量级可控（表 2-5 至表 2-8） |

现有做法与 VideoMind 的差别不是「能不能转写」，而是**转写之后的东西归属谁、能不能核对、能不能带走**。表 2-1 按使用者的困境逐条对照。

## 2.3 经济可行性（辅图 4）

### 2.3.1 成本结构

VideoMind 的成本可以分成两类：**本地计算**（一次性投入 + 零边际成本）与**云端调用**（按用量线性增长）。前者不随视频数量变化，后者才是需要估算的部分。

表 2-5 成本项分类（辅图 4 之一）

| # | 成本项 | 随使用量增长 | 计量口径 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | ASR 转写 | 否（本地） | 本机算力时间 | `faster-whisper` / `yueying` 在本机运行，无按次计费；初次使用需下载权重 |
| 2 | 关键帧 OCR | 否（本地） | 本机算力时间 | `RapidOCR`（onnxruntime）本地推理，无按次计费 |
| 3 | DeepSeek 结构化 | **是** | 输入 / 输出 token | 按量计费项只有这一项，见 2.3.2 |
| 4 | 存储 | 是（但量级小） | 本地磁盘 | 视频原片 + 关键帧；关键帧为 JPEG 缩略图 |
| 5 | 分发 | 一次性 | 构建与带宽 | 安装包约 271MB（NSIS）/ 338MB（便携 ZIP），GitHub Releases 托管 |

### 2.3.2 LLM 调用次数模型

调用次数直接决定 token 成本，且它与交付文档早期写法不同，需要以代码为准。

**代码事实**（`backend/app/llm.py:291-358`）：

- 转写按 `_TRANSCRIPT_LIMIT = 12000` 字符（`llm.py:137`）在**段边界**切块，每块独立调用一次 `_structure_chunk()`；
- 块数大于 1 时，额外调用一次 `_refine_summary()`（`llm.py:357`）做跨段收尾（一句话结论 + 标签）；
- 单块解析失败时重试一次（`llm.py:214` `for attempt in range(2)`），因此最坏情况每块 2 次；
- 无 API Key 时走 `fallback_draft()`（`llm.py:361`），**0 次调用**，产出为规则草稿并标注 `report["fallback"]`。

因此正常情况下的调用次数为：

```
调用次数 = 块数                      （块数 = 1）
调用次数 = 块数 + 1（合并收尾）        （块数 > 1）
最坏情况 = 2 × 块数 + 1               （每块都重试一次）
```

**一处必须纠正的口径**：`docs/交付与排期.md` §4.2 对辅图 4 的要求写作「须体现 F2/F3 各增一次 LLM 调用」，这与实现不符。F2（教学一致性校验，产出 `conflicts`）与 F3（易错点挖掘，产出 `pitfall`）都是 `_USER_TMPL`（`llm.py:69-75`）在同一次调用里要求的输出字段，`_SCHEMA`（`llm.py:79`）也只声明一个 `StructuredDraft` 结构——**F2/F3 不产生额外调用**。真正增加调用次数的是「分块 + 合并收尾」这套机制。本章按代码实际写，该处口径勘误已同步修正到 `docs/交付与排期.md`。

### 2.3.3 估算量与费用口径

### 2.3.4 功能维度与调用次数归集（辅图 4 之四）

成本表要同时回答两个问题：**设计时按什么口径估算**、**实现后实际是多少**。两者不一致时要并列给出，而不是二选一——只给估算会把实现说小，只给实现会把评审要看的成本意识弄丢。

表 2-8 功能维度与调用次数归集（辅图 4 之四）

| 功能 | 产出字段 | 代码位置 | 设计估算口径（按独立 pass） | 实现实测口径（当前代码） | 差额说明 |
| --- | --- | --- | --- | --- | --- |
| F1 证据链讲义 | `items[].evidence` | `llm.py:27` `DraftItem` | 1 次 / 块 | 与 F2/F3/F4 同一次调用内 | 合并 |
| F2 教学一致性校验 | `conflicts` | `llm.py:48` `StructuredDraft.conflicts` | **+1 次 / 块** | **+0 次**（同一次调用内的字段） | 合并，成本转为输出 token 增长 |
| F3 易错点挖掘 | `pitfall` | `llm.py:33` `DraftItem.pitfall` | **+1 次 / 块** | **+0 次**（同一次调用内的字段） | 合并，成本转为输出 token 增长 |
| F4 不确定性分级 | `confidence` | `llm.py:27` `DraftItem` | 1 次 / 块 | 与 F1/F2/F3 同一次调用内 | 合并 |
| 分块与合并收尾 | — | `llm.py:291` `structure()`、`llm.py:252` `_refine_summary()` | 每块 1 次 + 1 次收尾 | **同左**（这是成本的真正大头） | 无差额 |
| 解析失败重试 | — | `llm.py:214` `for attempt in range(2)` | 未计 | **最坏每块 +1 次** | 实现侧新增风险项 |

> **两种口径的算式**（`块数` 由 `llm.py:158` `_chunk_transcript()` 按段边界切分决定）：
>
> - **设计估算口径**（视 F1–F4 各自独立 pass，`交付与排期.md:107` 的题意）：`调用次数 = 4 × 块数 + 1`；
> - **实现实测口径**（`_SCHEMA = StructuredDraft.model_json_schema()`，一次要求全部字段，`_structure_chunk` 每块只发一次 `_chat`，见 `llm.py:217`）：`调用次数 = 块数 + 1`；
> - **最坏情况**（每块解析失败重试一次）：`调用次数 = 2 × 块数 + 1`。
>
> 按表 2-6 的块数代入：30 分钟（1 块）设计 5 次 / 实现 2 次 / 最坏 3 次；90 分钟（2 块）设计 9 次 / 实现 3 次 / 最坏 5 次；3 小时（4 块）设计 17 次 / 实现 5 次 / 最坏 9 次。
>
> **F2/F3 合并进同一次调用，成本并非为零**：省下的是调用次数，新增的是**输出 token**（多两个字段的长度）与**重试概率**（输出结构越复杂越容易解析失败，触发 `llm.py:214` 的重试或 `llm.py:142` 的截断抢救）。因此「设计时以为要 4 次、实现合并成 1 次」是真实的工程收益，但不能读作零成本。
>
> **表 2-8 注（口径勘误）**：F2/F3 原按独立调用估算，实现期合并进同一次结构化调用，**调用次数不增，成本体现为输出 token 与重试概率**；此为对 `docs/交付与排期.md:107` 口径的实测勘误，已记入 `CHANGELOG.md` 的 v0.17 条目。
>
> 另需分清一处措辞：`docs/交付与排期.md` §4.2 原文把 F3 写作「多产物」，而 `docs/产品定义.md:87` 与代码（`DraftItem.pitfall`）都是「易错点挖掘」。多产物指的是 `artifacts.py` 的 `OutputSchemaStrategy`（讲义 / UML 草稿 / 总结 / 要点 / 代码块）这一层，**纯本地计算，不产生任何 LLM 调用**——这是两件不同的事，不应混为一谈。

### 2.3.5 成本可控的三个机制

| 机制 | 实现位置 | 作用 |
| --- | --- | --- |
| 画面文字按时间归属 | `llm.py:180` `_allocate_ocr()` | 每块只看自己时间范围内的 OCR，同一段画面文字不会被重复计费 |
| 输出上限约束 | `llm.py:138` `_MAX_TOKENS_STRUCTURE = 8000` | 单次输出有硬上限，不会因模型发散无限增长 |
| 提示词规模约束 | `llm.py:56` items ≤ 15 条、content ≤ 120 字 | 压低输出 token，同时降低截断风险 |

**经济可行性结论**：本项目不含任何按次计费的基础设施；按量计费项只有 LLM 结构化这一项，其成本由调用次数（表 2-6）与输出上限（`_MAX_TOKENS_STRUCTURE`）双重夹住，与视频总时长近似线性且系数很小。课程演示规模（数十条视频）下不构成障碍。

### 2.4.1 三条运行路径及其前提

表 2-9 运行路径对照

| 路径 | 适用场景 | 前提条件 | 边界 |
| --- | --- | --- | --- |
| 源码运行 | 开发、出截图与录屏 | 后端 `backend/.venv` + 前端 `npm install`；`.env` 填 `DEEPSEEK_API_KEY` | 需本机具备 Node 与 Python 3.14 环境 |

> 同时，Docker 演示若不填 Key，结构化会走 `fallback_draft()` 规则草稿，`report["fallback"]` 标注为真——**这条路径可以用来验证链路通不通，不能用来展示模型效果**。

## 2.6 小结

1. **技术可行**：四个阶段与三个可插拔策略均已实现并可指到 `backend/app/` 下的具体位置；测试基线全绿（2.2.2）。
2. **经济可行**：ASR 与 OCR 本地运行无边际成本；按量计费项只有 LLM 结构化这一项，调用次数由分块机制决定、输出受 8000 token 上限约束（2.3.2、2.3.5）。**本章给出 token 量级而不给货币金额**，因为单价是变量、公式才是结论。
3. **操作可行**：三条运行路径各有明确前提，其中 Docker 路径的文件名约束与「不可展示模型效果」两条边界已如实写明（2.4）。
4. **进度可行但已有偏差**：W2–W4 的图与原型未落盘，偏差源于分支未合入而非功能缺失；剩余缓冲已在 v0.17 重新分配（2.5）。
5. **辅图 4 按两种口径同时给出**：评分口径要求的「F2/F3 各增一次调用」按分项独立 pass 估算为 `4 × 块数 + 1`；当前实现把 F1–F4 合并在同一次调用里，实际为 `块数 + 1`。两列都列（表 2-8），并说明了这处交付侧措辞与代码的差异原因（2.3.4）。
